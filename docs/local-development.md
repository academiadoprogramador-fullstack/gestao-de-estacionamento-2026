# Configuração local de desenvolvimento

A API encerra o startup antes de abrir qualquer endpoint quando uma configuração obrigatória estiver ausente ou inválida. Em desenvolvimento local, use o User Secrets da API (`app/backend/src/Estacionamento.Api/Estacionamento.Api.csproj`) para a conexão e senhas sintéticas; o `.env` do Docker Compose serve apenas ao contêiner SQL Server. Não coloque credenciais ou chaves em arquivos versionados. User Secrets não é criptografado e não deve guardar credenciais de produção.

| Chave de configuração (equivalente no ambiente) | Obrigatória | Uso |
| --- | --- | --- |
| `ConnectionStrings__Identity` | Sim | Conexão com banco SQL Server isolado para o ambiente atual. |
| `Security__SpaOrigin` | Sim | Origem HTTPS permitida para a SPA, sem caminho adicional. |
| `DataProtection__KeyRingPath` | Sim | Diretório persistente de Data Protection isolado por ambiente. |
| `MSSQL_SA_PASSWORD` | Ao iniciar SQL Server Compose | Senha local do SQL Server Developer; pode ser definida em `app/backend/.env` (ignorado pelo Git) ou no ambiente do shell. Não a compartilhe entre ambientes. |
| `TEST_SQLSERVER_CONNECTION` | Ao executar testes de integração | Conexão a uma base dedicada nomeada `Estacionamento*`; factories/provisionamento recusam catálogos vazios, system DBs e nomes de Development/Local/Production. |
| `TEST_MIGRATION_SQLSERVER_CONNECTION` | Ao verificar a migração inicial | Conexão a uma base dedicada vazia `Estacionamento*`, distinta da base de integração. |
| `TEST_VALET_PASSWORD`, `TEST_CASHIER_PASSWORD`, `TEST_ADMIN_PASSWORD` | Ao executar integração/E2E | Senhas sintéticas de bancos de teste isolados. No E2E local, podem vir dos User Secrets de desenvolvimento da API, desde que a conexão aponte para um banco de teste distinto. Nunca use credenciais de produção. |
| `TEST_IDEMPOTENCY_HMAC_KEY` | Opcional no E2E local | Chave de teste Base64 de pelo menos 32 bytes; se omitida, o Playwright gera uma chave efêmera para o processo de API daquele run. Não reutilize banco E2E entre runs com chave efêmera se depender de replay de resultados anteriores. |
| `SyntheticAccounts__ValetPassword` | Ao provisionar conta sintética local | Senha fornecida por canal local seguro; nunca versionada. |
| `SyntheticAccounts__CashierPassword` | Ao provisionar conta sintética local | Senha fornecida por canal local seguro; nunca versionada. |
| `SyntheticAccounts__AdministratorPassword` | Ao provisionar conta sintética local | Senha fornecida por canal local seguro; nunca versionada. |
| `Idempotency__Hmac__ActiveKeyVersion` | Sim | Versão numérica da chave HMAC usada em novos check-ins. |
| `Idempotency__Hmac__Keys__{versão}` | Sim | Chave HMAC externa em Base64 com pelo menos 32 bytes; conservar cada versão referenciada por resultados idempotentes. |

A duração de inatividade da sessão pode ser configurada por `Authentication__IdleTimeoutSeconds` (padrão local de 1200 segundos).

O protocolo de idempotência exige segredo HMAC separado das senhas e do key ring de Data Protection. Gere uma chave local com `openssl rand -base64 32` e configure `Idempotency:Hmac:ActiveKeyVersion` e `Idempotency:Hmac:Keys:1` via User Secrets/ambiente; não inclua o valor gerado em arquivos versionados nem em logs. Na rotação, adicione uma nova chave versionada e altere a versão ativa, mantendo configuradas as versões anteriores enquanto houver resultados que as referenciem. As chaves não são incluídas no banco: perder uma versão antiga impede comparar com segurança os retries daquele conjunto de resultados, portanto nenhuma remoção/TTL é automatizada nesta fase. A canonicalização v1 inclui somente placa, modelo, titular, documento, vistoria e ID da vaga normalizados, em ordem fixa; corpo pessoal não é persistido como chave de comparação.

Para `POST /api/v1/attendances`, o cliente gera um UUID não vazio por tentativa e o envia em `Idempotency-Key`. Se a conexão expirar ou a resposta não chegar, o resultado é **desconhecido**, não uma falha confirmada: mantenha chave e conteúdo somente em memória e repita o mesmo comando, para o mesmo funcionário, com a mesma chave. O servidor devolve o resultado original quando a operação já foi confirmada; conteúdo diferente com a mesma chave recebe `409 Conflict`. Não gere outra chave como reação ao timeout. Se a tela/requisição for perdida, autentique-se e pesquise o atendimento antes de decidir iniciar uma nova ação; não há endpoint de consulta por chave. Uma sessão revogada recebe `401` também no replay e precisa de novo login. Resultados e chaves não expiram nem são limpos automaticamente nesta fase; retenção/TTL exige decisão explícita futura. A chave de idempotência não contém os dados da tentativa: somente o HMAC com versão fica persistido junto ao resultado mínimo.

O diretório configurado em `DataProtection:KeyRingPath` contém o key ring local usado também pela proteção de campos sensíveis. Restrinja o acesso ao usuário do processo e preserve esse diretório junto com o banco local: remover chaves antigas pode tornar documentos e vistorias já cifrados irrecuperáveis. A proteção usa propósitos versionados separados por atendimento/campo e um envelope que identifica a versão do formato e do propósito; indisponibilidade de uma chave histórica deve resultar em falha controlada, nunca em conteúdo vazio. Não copie nem compartilhe o key ring como exemplo, não o inclua no Git e não trate esta configuração local como procedimento aprovado de backup, retenção, recuperação ou gestão de chaves para produção. Esses controles continuam pendentes de validação na Fase 5.

Em `Development`, as três contas sintéticas são criadas somente quando ainda não existem, usando as senhas externas `SyntheticAccounts:ValetPassword`, `SyntheticAccounts:CashierPassword` e `SyntheticAccounts:AdministratorPassword`. Depois da criação, o bootstrap não redefine senhas, não reativa contas e não repõe perfis removidos; gerencie-as pela API administrativa autenticada ou por operação local explicitamente controlada. Para a primeira preparação, mantenha uma conta administradora ativa acessível e use origem HTTPS local com antiforgery. `GET/POST /api/v1/employees` e `PUT /api/v1/employees/{id}/access` exigem perfil administrador; a senha inicial é processada pelo Identity e nunca retornada. Alterar perfis ou estado invalida o security stamp, então cookies existentes deixam de autorizar a próxima requisição protegida e o funcionário precisa autenticar novamente para receber os papéis atuais. A proteção do último administrador ativo e conflitos de versão são aplicados pelo servidor.

Vagas são preparadas por administrador em `POST /api/v1/spaces` e consultadas pelos três perfis em `GET /api/v1/spaces?code=A-01&status=free&page=1&pageSize=20`; códigos são aparados e normalizados em maiúsculas, e `status` aceita `free` ou `occupied`. A disponibilidade é uma leitura informativa e não reserva a vaga: o servidor valida novamente no check-in. Esta fase não oferece liberação manual de ocupação.

A tarifa não tem valor inicial. Administradores consultam `GET /api/v1/daily-rates/current` e o histórico paginado em `GET /api/v1/daily-rates`; a resposta corrente fornece uma `version` opaca para publicar em `POST /api/v1/daily-rates` junto com `amount`, por exemplo `{"amount": 12.34, "baseVersion": "VERSAO_OPACA_RECEBIDA"}`. O número no exemplo é **sintético** e não define moeda, tarifa comercial ou valor de teste obrigatório. Valores devem ser positivos, ter no máximo duas casas decimais, e uma versão-base obsoleta recebe `409 Conflict`; em conflito, consulte novamente a versão corrente antes de uma nova publicação intencional. Versões publicadas permanecem imutáveis. Horários persistidos/respostas são UTC; moeda e fuso de apresentação reais continuam pendentes, sem inferência por esses exemplos.

## Navegação e telas da Fase 2

Após autenticar, a SPA mantém a sessão somente no cookie HttpOnly; sinais Angular guardam o estado em memória e não há persistência de sessão em `localStorage`/`sessionStorage`. Rotas e navegação: `/dashboard` para qualquer perfil; `/spaces` e `/attendances` para manobrista, caixa e admin; `/check-in` apenas caixa/admin; `/employees` e `/daily-rates` apenas admin. Sessão ausente ou revogada volta para login; rota/ação sem permissão apresenta acesso negado, enquanto a API continua sendo a autoridade de autorização. Admin pode cadastrar funcionários com senha inicial e perfis, alterar estado/perfis com concorrência otimista, cadastrar vagas e publicar tarifa versionada. A senha inicial é apagada da tela após a confirmação. A tela de vagas permite filtrar código/situação e paginar; sua disponibilidade é informativa e não reserva vaga.

O seletor de check-in pagina as vagas livres em lotes de 100 e tem atualização manual; isso não é limite de vagas da unidade e não reserva a seleção. Se a lista falhar inicialmente, use “Atualizar vagas”. O histórico de tarifas também pagina (20 por página) e possui ação de atualização/retry após erro. Validações administrativas apresentam resumo com foco e marcação dos campos inválidos. Resultados assíncronos de atendimento antigos são ignorados após troca/fechamento do detalhe. Durante POST de entrada, troca de rota/logout é bloqueada e reload/fechamento do navegador aciona confirmação; se o usuário confirmar a saída, tentativa não é recuperável porque os dados não são persistidos no browser.

A consulta de vagas atualiza por polling local padrão de **15 segundos**, configurado pelo provider `SPACE_AVAILABILITY_POLL_INTERVAL_MS` em `app/frontend/src/app/core/admin/admin-pages.ts` (o provider pode ser sobrescrito em `app.config.ts` ou nos testes). O polling pausa quando a aba fica oculta, reinicia/refaz a consulta ao recuperar visibilidade ou foco, e uma consulta em andamento impede sobreposição; filtros, paginação e cadastro disparam releitura. Ao sair da rota, a inscrição é encerrada e a requisição HTTP observável é cancelada. O tempo de polling é uma escolha local de UI, não requisito operacional nem mecanismo de reserva.

## Roteiro local de acessibilidade da UI

Sem declarar conformidade normativa ou validação operacional, faça uma verificação manual das rotas `/employees`, `/spaces`, `/daily-rates`, `/check-in` e `/attendances` usando apenas teclado: percorra os controles com `Tab`/`Shift+Tab`, acione botões/links com `Enter` ou `Space`, confirme que o foco visível não se perde e que não há armadilha de foco. Envie formulários vazios e confirme resumo de erros anunciado e foco levado ao resumo; teste mensagens de carregamento, vazio, sucesso e falha; use zoom do navegador e viewport estreito para conferir reflow sem perda de conteúdo/ação. Nas telas de atendimento, valide que leitura de documento é ação explícita apenas para caixa/admin, leitura de vistoria é explícita e mensagens de estado são anunciadas. Em check-in, teste navegação por rota e o diálogo de resultado desconhecido sem recarregar até o replay resolver a tentativa. Registre navegador, perfis sintéticos e observações ao executar; testes de componente verificam semântica/foco básico, mas não substituem este roteiro manual nem avaliação de acessibilidade formal.

Em `Development`, o startup da API aplica migrações pendentes e provisiona idempotentemente as três contas/papéis sintéticos antes de abrir endpoints. Falha de conexão ou ausência de qualquer senha impede o startup. Senhas vêm do User Secrets/ambiente e não são redefinidas para contas já existentes. Fora de `Development` não há migração nem provisionamento automático; o comando legado `dotnet run --project app/backend/src/Estacionamento.Api -- --provision-synthetic-accounts` permanece disponível somente no ambiente local.

O `app/backend/docker-compose.yml` exige `MSSQL_SA_PASSWORD` e não fornece valor padrão. Para iniciar o banco com a senha definida em `app/backend/.env`, execute `cd app/backend && docker compose up -d`; o arquivo é local e não deve ser versionado. Uma variável já definida no shell tem precedência sobre o `.env`. Use a mesma senha na conexão da API; se o volume do banco já existir, alterar apenas o `.env` não altera a senha do SQL Server existente. A origem, o caminho do key ring e as conexões não possuem fallback silencioso. Configurações e chaves de teste devem permanecer separadas de quaisquer valores ou recursos de produção.

O projeto da API já tem `UserSecretsId`. Para configurar ou atualizar os valores locais (sem incluir segredos no repositório), execute de `app/backend/`:

```bash
dotnet user-secrets set 'ConnectionStrings:Identity' 'Server=localhost,14333;Database=EstacionamentoDev;User Id=sa;Password=SENHA_DO_ARQUIVO_BACKEND_DOT_ENV;Encrypt=True;TrustServerCertificate=True' --project src/Estacionamento.Api
dotnet user-secrets set 'Security:SpaOrigin' 'https://localhost:4200' --project src/Estacionamento.Api
dotnet user-secrets set 'DataProtection:KeyRingPath' "$HOME/.local/share/estacionamento/key-ring" --project src/Estacionamento.Api
dotnet user-secrets set 'SyntheticAccounts:ValetPassword' 'SENHA_LOCAL_FORTE' --project src/Estacionamento.Api
dotnet user-secrets set 'SyntheticAccounts:CashierPassword' 'SENHA_LOCAL_FORTE' --project src/Estacionamento.Api
dotnet user-secrets set 'SyntheticAccounts:AdministratorPassword' 'SENHA_LOCAL_FORTE' --project src/Estacionamento.Api
```

Substitua os exemplos por senhas distintas e fortes em cada máquina. `dotnet user-secrets list --project src/Estacionamento.Api` revela os valores em texto claro: evite usá-lo em logs ou capturas de tela. Inicie a API em `Development` com `dotnet run --project src/Estacionamento.Api --no-launch-profile --urls http://127.0.0.1:5188` (defina `ASPNETCORE_ENVIRONMENT=Development` no shell). Variáveis de ambiente com os nomes da tabela têm precedência sobre User Secrets.

O harness Playwright em `app/frontend/e2e/` lê o `.env` local desse diretório (copie `.env.example` e preencha conexão e senhas de teste); variáveis já definidas no ambiente têm precedência. É possível usar as três senhas sintéticas dos User Secrets da API local, mas `TEST_SQLSERVER_CONNECTION` **deve apontar a um banco dedicado cujo nome começa por `EstacionamentoE2E`**. O próprio `playwright.config.ts` rejeita bancos `master`/reservados, de desenvolvimento ou com outro nome antes de iniciar a API, e nunca reutiliza uma API já em execução para evitar migrations no processo/banco errado. Para o teste de migração .NET, use outro banco vazio dedicado (`EstacionamentoE2EMigration`). O `.env` é ignorado pelo Git e não deve conter credenciais de produção. Esse arquivo não configura automaticamente os testes de integração .NET: exporte as mesmas variáveis de teste no shell ao executar `dotnet test`. O harness serve a SPA em `https://localhost:4200` e encaminha somente `/api/*` para o upstream fixo `http://127.0.0.1:5188`. O cabeçalho `X-Forwarded-Proto` é confiado pela API apenas por meio do proxy loopback de desenvolvimento. A porta da API é acessível localmente para testes diretos; esse arranjo não representa nem comprova restrição de ingresso entre sites numa implantação Azure.

## Revisão e aplicação controlada de migrações fora do bootstrap local

O histórico do contexto `IdentityDbContext` contém as migrações `InitialIdentity` e `AddEmployeeActiveStatus`, seguidas pela migration aditiva `AddOperationalModules`. A migration operacional acrescenta os módulos de estacionamento, tarifa, atendimento, vistoria, ocupação, auditoria e idempotência; cria as linhas técnicas singleton sem publicar tarifa nem cadastrar vagas; e substitui o índice de e-mail por índice único. Antes de criar essa unicidade, verifica duplicatas normalizadas e falha com diagnóstico, sem apagar ou alterar contas. Em caso de duplicatas históricas, corrija-as manualmente após investigação e backup local antes de tentar novamente.

O contrato OpenAPI é gerado no build da API em `app/backend/src/Estacionamento.Api/obj/Estacionamento.Api.json` (pacotes .NET 10 fixados e restore travado); execute `dotnet restore --locked-mode` e `dotnet build` para recriá-lo. Não há Swagger UI. A rota runtime `/openapi/v1.json` não é mapeada por padrão; somente pode ser habilitada em ambiente `Development` com `OpenApi__Expose=true`, e exige sessão de administrador. Não habilite essa opção em ambientes compartilhados/produção; distribua o artefato gerado localmente conforme o fluxo autorizado.

Em `Development`, as migrações pendentes são aplicadas automaticamente no startup, exclusivamente ao banco local configurado. Testes e outros ambientes não executam migrações no startup; as fixtures de integração aplicam migrations explicitamente em bancos isolados. Para revisar o SQL e testar a reconstrução/upgrade local, use **somente** conexões de bancos sintéticos dedicados:

```bash
cd app/backend
dotnet tool restore
ConnectionStrings__Identity="$IDENTITY_TEST_CONNECTION" dotnet ef migrations script --idempotent --project src/Estacionamento.Infrastructure/Estacionamento.Infrastructure.csproj --startup-project src/Estacionamento.Api/Estacionamento.Api.csproj
ConnectionStrings__Identity="$IDENTITY_TEST_CONNECTION" dotnet ef database update --project src/Estacionamento.Infrastructure/Estacionamento.Infrastructure.csproj --startup-project src/Estacionamento.Api/Estacionamento.Api.csproj
```

Para verificar reconstrução em banco vazio e upgrade de contas Identity, exporte `TEST_SQLSERVER_CONNECTION` e `TEST_MIGRATION_SQLSERVER_CONNECTION` para bases sintéticas dedicadas nomeadas `Estacionamento*`, distintas entre si, e execute `dotnet test tests/Estacionamento.IntegrationTests/Estacionamento.IntegrationTests.csproj`. Factories, provisionamento sintético e teste de migration validam nomes antes de inicializar banco; outros helpers criam bases com nome aleatório de teste. Nunca use `master`, `model`, `msdb`, `tempdb` nem a base de desenvolvimento como destino de teste. A barreira pelo nome é defesa contra erro de configuração, não isolamento de rede/permissão.

Recuperação local é não destrutiva: se uma versão do aplicativo precisar ser revertida, mantenha o esquema aditivo e os dados, e use uma versão compatível com esse esquema ou corrija a migration com outra alteração aditiva. Não execute `Down` como recuperação, não apague registros confirmados e não recrie/apague a base de desenvolvimento para contornar falha. Bases temporárias pertencentes aos testes podem ser limpas pelo próprio harness após a execução. Nenhum comando desta seção se destina a Azure; migrations Azure e ambientes publicados permanecem fora desta fase.

Os testes de integração iniciam a API em `Testing`, sem carregar User Secrets nem executar o bootstrap local; exigem `TEST_SQLSERVER_CONNECTION` e as senhas de teste acima. O harness E2E inicia a API em `Development` com banco de teste próprio e passa as três senhas via ambiente, exercitando também a migração e o provisionamento automáticos.
